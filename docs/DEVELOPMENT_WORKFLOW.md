# Процесс разработки — Metacritic Games Service

**Версия:** 1.0
**Дата:** 2026-09-07

---

## 1. Принципы

1. **Сначала исследование, потом реализация.** Не изобретать API-контракты и селекторы.
   Неподтверждённая разметка → OPEN QUESTION и задача на исследование, а не догадка в коде.
2. **Значимые решения оформляются ADR.** Решение без ADR считается неоформленным.
3. **Критичные допущения фиксируются в документации**, а не в комментариях к коду.
4. **Границы модулей проверяются автоматически**, а не на code review.
5. **Идемпотентность по умолчанию** для всех фоновых задач.
6. **Внешний ввод недоверенный** — и Metacritic, и YouTube, и ответы LLM.

## 3. AI development logs (требование заказчика)

Решение по OQ-16 — обязательное к исполнению:

- Полная AI development history сохраняется.
- Raw logs **не редактируются**.
- Логи разных AI-агентов хранятся **отдельно**.
- Дополнительно ведётся **merged JSONL audit trail**.
- В merged log обязательны: `agent`, `role`, `timestamp`, тип сообщения/события.

### 3.1 Сырые логи (неизменяемые)

```
logs/ai/raw/
├── claude-code/
│   └── 2026-09-07-session-01.jsonl
└── <другой-агент>/
    └── ...
```

Правила: append-only, без постобработки, без переформатирования, по одному JSON-объекту на
строку. Именование: `<YYYY-MM-DD>-session-<NN>.jsonl`.

### 3.2 Merged audit trail

`logs/ai/merged/ai-conversation.jsonl` — сведённая хронология всех агентов данного проекта:

```json
{
  "timestamp": "2026-09-07T14:23:11.482Z",
  "agent": "claude-code",
  "session_id": "38571e61-...",
  "role": "assistant",
  "event_type": "message",
  "sequence": 42,
  "content": "...",
  "metadata": { "model": "claude-opus-5", "tokens_in": 1200, "tokens_out": 340 }
}
```

Обязательные поля: `timestamp` (ISO 8601, UTC), `agent`, `role`
(`user`/`assistant`/`system`/`tool`), `event_type`
(`message`/`tool_call`/`tool_result`/`error`), `sequence`.

Merged-лог включает **только взаимодействия по этому проекту** (OQ-20). Он формируется
скриптом из raw-логов и является производным артефактом: при расхождении источником истины
считаются raw-логи. Пересборка — `npm run logs:merge`.

### 3.3 Runtime AI-логи сервиса

Отдельно от логов разработки: `logs/ai/runtime/llm-calls.jsonl` — все обращения сервиса к
LLM в проде (промпт, ответ, модель, токены, длительность, `game_slug`).

### 3.4 Секреты и неизменяемость (OQ-19)

Требование «raw logs не редактируются» конфликтует с обычной практикой затирания секретов.
Разрешение конфликта — **не допускать попадания секретов в логи вообще**:

1. API-ключи никогда не передаются в промпты и не логируются (запрет на уровне кода).
2. Перед публикацией репозитория выполняется автоматический скан секретов
   (`npm run logs:scan`).
3. Запрещено автоматически изменять содержимое raw log после записи.
4. При обнаружении секрета — **остановить публикацию и сообщить Product/Tech Lead**.
   Ретроспективное маскирование raw conversation запрещено.

Так raw-логи остаются нетронутыми, а ключ не попадает в публичный репозиторий.

## 4. Git-процесс

**Ветки:** `main` (стабильно), `feat/*`, `fix/*`, `docs/*`, `chore/*`.

**Коммиты:** Conventional Commits — `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`.

**Правила:**
- Один коммит — одно логическое изменение.
- Коммиты, меняющие архитектуру, ссылаются на ADR (`Refs: ADR-0004`).
- Push и деплой — только по явной команде Product/Tech Lead.

## 5. Тестирование

| Уровень | Что покрывает | Зависимости |
|---|---|---|
| **Unit** | Доменные правила: день-план, claim/lease, идентичность | Нет (без БД и сети) |
| **Integration** | Репозитории, конкурентный claim, миграции | PostgreSQL |
| **Parser (golden-file)** | Парсинг на зафиксированном HTML | Фикстуры |
| **E2E (smoke)** | Запуск → БД → отображение в UI | Docker Compose |

### Обязательные тесты корректности (по ADR-0004)

- Параллельный claim одного слага двумя воркерами → успешен ровно один.
- Повторный запуск в тот же день → нет второго claim.
- Истёкший lease → reaper возвращает игру в пул, без дубля.
- Перезапуск после части стадий → продолжение, а не начало заново.
- Пересечение страниц листинга → ни одна игра не пропущена.

### Golden-file тесты парсеров

HTML-фикстуры реальных страниц Metacritic фиксируются в `tests/fixtures/`. Это ловит
редизайн сайта в CI, а не потерей данных в проде. Обязательные фикстуры включают
`the-blood-of-dawnwalker` — подтверждённый случай **отсутствующего developer**
**[ПРОВЕРЕНО]**.

## 6. CI

Пайплайн на каждый push:

1. Lint + форматирование.
2. Проверка типов (`tsc --noEmit`).
3. **Проверка границ модулей** (`dependency-cruiser`) — `domain` не импортирует
   `infrastructure`; нарушение = падение сборки (ADR-0001).
4. Unit-тесты.
5. Integration-тесты (PostgreSQL в контейнере).
6. Сборка Docker-образа.

## 7. Конфигурация

Все настройки — через environment, валидация схемой при старте: приложение падает сразу при
неверной конфигурации, а не в середине обработки.

```
DATABASE_URL=
PROCESSING_TIMEZONE=UTC          # OQ-1
BATCH_SIZE=20                    # OQ-13
WORKER_CONCURRENCY=4
METACRITIC_RATE_LIMIT_RPS=1
HTTP_TIMEOUT_MS=15000
CLAIM_LEASE_MINUTES=10
MAX_ATTEMPTS=3
LLM_MODEL=<организация>/<модель>  # шлюз OpenRouter (ADR-0006)
LLM_MODEL=                       # конкретная модель — только через конфиг
LLM_API_KEY=                     # только env; никогда не логируется
ADMIN_TOKEN=                     # ADR-0007; constant-time сравнение, не логируется
FEATURE_YOUTUBE_ENABLED=false    # ADR-0005
YOUTUBE_API_KEY=
```

## 9. Порядок работы с открытыми вопросами

1. Обнаружена неоднозначность → запись в `OPEN_QUESTIONS.md` с вариантами и рекомендацией.
2. Если вопрос **блокирующий** — работа по нему останавливается до решения; остальные задачи
   продолжаются.
3. Если **не блокирующий** — реализация идёт по рекомендованному варианту, допущение
   фиксируется в документации.
4. Решение принято → вопрос помечается закрытым, при необходимости оформляется ADR.

Молчаливое додумывание требований не допускается.
