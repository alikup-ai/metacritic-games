# Суточная обработка: заявки, запуски, воркеры, планировщик

**Версия:** 1.1 (Hardening Pass)
**Дата:** 2026-09-07
**Область:** Phase 1C — daily processing, DailyClaim, worker pool, scheduler

---

## 1. Почему реестр заявок — источник истины

Требование ТЗ: каждый час обрабатывать **20 игр, которые сегодня ещё не обрабатывались**.
Отсюда нужен ответ на вопрос «обрабатывали ли мы эту игру сегодня», и ответ обязан
переживать перезапуск приложения.

Таблица `daily_claims` даёт этот ответ первичным ключом:

```sql
PRIMARY KEY (processing_day, source, source_slug)
```

Захват выполняется атомарно:

```sql
INSERT ... ON CONFLICT (processing_day, source, source_slug) DO NOTHING RETURNING *
```

Возвращённая строка означает «игра захвачена именно этим вызовом». Пустой результат —
«кто-то уже взял её сегодня». Двойной захват физически невозможен: это ограничение СУБД,
а не соглашение в коде, и обойти его из приложения нельзя.

**Разделение ответственности с блокировкой** (требование §7):

| Механизм | За что отвечает |
|---|---|
| Advisory lock | Не даёт двум запускам делать лишнюю параллельную работу |
| **Реестр заявок** | **Гарантирует идемпотентность** |

Даже если блокировка потеряна, два процесса стартовали одновременно или планировщик
запустил повторный проход — двойной обработки не будет. Блокировка лишь экономит ресурсы;
корректность обеспечивает реестр.

## 2. Почему пагинация — только подсказка

Листинг Metacritic **дрейфует**. Замер на фикстурах, снятых с интервалом ~1.3 секунды,
показал **5 общих игр из 20** между страницами 1 и 2, смещённых по позициям
(1→4, 2→3, 15→17). За час между запусками сдвиг будет значительно больше.

Предположение «страница 2 = игры 21..40» неверно. Логика «одна страница за запуск»
приводила бы одновременно к двум ошибкам:

- **повторам** — игра со страницы 1 уезжает на страницу 2 и читается снова;
- **молчаливым пропускам** — игра из «слепой зоны» между снимками не читается никогда.

Поэтому `processing_days.browse_page` — **подсказка**, экономящая запросы, а не источник
истины. Алгоритм листает страницы, отбрасывая уже заявленные слаги, пока не наберёт нужное
число действительно новых заявок.

---

## 3. Что означает «20 игр»

**20 = 20 уникальных игр, успешно ЗАЯВЛЕННЫХ (claimed) в текущие сутки.**

Это не 20 успешно завершённых обработок. Если ingestion заявленной игры упал:

- заявка **остаётся** в реестре;
- ошибка фиксируется в `last_error` и `stages`;
- повтор работает с **той же** заявкой;
- новая заявка на эту игру сегодня **не создаётся**.

Обоснование: «до 20 успехов» означало бы неограниченное число запросов к источнику именно
тогда, когда он нестабилен — то есть усиление нагрузки в момент, когда следует
отступить. Ограниченный батч предсказуем; механизмом повтора служит сам почасовой график.

## 4. Алгоритм поиска 20 уникальных игр

```
ensureDay(processingDay)          — новый день создаётся с фазой new_releases
    ↓
пока собрано < 20:
    ├─ проверить лимит страниц (MAX_PAGES_PER_RUN)
    ├─ получить страницу листинга
    ├─ вычислить отпечаток набора слагов
    │     └─ отпечаток уже встречался → стоп (repeated_page)
    ├─ страница без карточек → счётчик пустых + 1
    │     └─ достиг MAX_EMPTY_PAGES → стоп (source_exhausted)
    ├─ атомарно заявить кандидатов (LIMIT после отсева заявленных)
    │     └─ уже заявленные отсеиваются СУБД
    ├─ ноль новых заявок, но карточки были → счётчик насыщения + 1
    │     └─ достиг отдельного, втрое большего порога → стоп (saturated)
    └─ раздел new_releases пройден → переключить фазу на browse
    ↓
сохранить курсор страницы (подсказка)
```

### Защита от зацикливания

| Риск | Защита | Сила сигнала |
|---|---|---|
| Источник отдаёт одну и ту же страницу | Отпечаток набора слагов, а не номера страницы | **Сильный** — остановка |
| Страница без единой карточки | `MAX_EMPTY_PAGES` (по умолчанию 3) | **Сильный** — источник закончился |
| Все игры на странице уже заявлены | Отдельный, втрое больший порог | Слабый — штатный дрейф |
| Бесконечное листание | `MAX_PAGES_PER_RUN` (по умолчанию 25) | Защитный предел |
| Некорректный курсор | `Math.max(1, browsePage)` при чтении | — |
| Ошибка источника | Прерывание с `stopReason = source_error` | — |

### Почему «пусто» и «всё уже заявлено» разделены

Эти состояния выглядят одинаково (новых заявок ноль), но означают разное:

- **страница без карточек** — источник физически закончился, продолжать бессмысленно;
- **страница, где все игры уже заявлены** — нормальное следствие дрейфа пагинации, особенно
  ближе к концу суточной выборки.

Если считать их одинаково, три подряд «насыщенные» страницы остановили бы поиск, хотя
новые игры лежали бы на четвёртой. Поэтому для насыщения действует отдельный порог
(`max(MAX_EMPTY_PAGES × 3, MAX_PAGES_PER_RUN)`), а основными сигналами остановки служат
повтор отпечатка страницы и действительно пустые страницы.

Причины остановки различаются в отчёте: `source_exhausted`, `saturated`, `repeated_page`,
`page_limit`, `target_reached`, `source_error`.

Отпечаток берётся именно от **набора слагов**: источник может отдавать одинаковое
содержимое под разными номерами страниц, и проверка по номеру этого не поймала бы.

### Захват ровно нужного количества

Заявки создаются одним запросом, где `LIMIT` применяется **после** отсева уже заявленных:

```sql
INSERT INTO daily_claims (...)
SELECT ... FROM unnest($4::text[], $5::text[]) AS c(source, slug)
WHERE NOT EXISTS (
  SELECT 1 FROM daily_claims existing
  WHERE existing.processing_day = $1 AND existing.source = c.source
    AND existing.source_slug = c.slug
)
LIMIT $6
ON CONFLICT (processing_day, source, source_slug) DO NOTHING
RETURNING ...
```

Вставляется ровно нужное количество: **лишние заявки не захватываются даже временно**, и
удалять ничего не требуется. `ON CONFLICT` остаётся страховкой от гонки — между проверкой
`NOT EXISTS` и вставкой другой процесс может успеть создать ту же строку; тогда запрос
вернёт меньше строк, а недостача доберётся со следующей страницы.

> **История дефектов этого места.** Первая версия обрезала кандидатов по лимиту **до**
> вставки: уже заявленные «съедали» лимит, и заявок выходило меньше (тест 8 дал 15 вместо
> 20). Вторая версия вставляла всех кандидатов и удаляла излишек — это устраняло недобор,
> но временно захватывало лишние игры, и падение между `INSERT` и `DELETE` оставило бы их
> заблокированными до истечения аренды. Текущая версия не создаёт излишка вовсе.

## 5. Новые сутки

Каждые новые сутки обработка начинается **заново с раздела New Releases**:

- отсутствие строки в `processing_days` → создаётся с `phase = 'new_releases'`,
  `browse_page = 1`;
- вчерашний курсор не продолжается;
- вчерашние заявки остаются в БД и **не мешают**: первичный ключ включает сутки, поэтому
  та же игра заявляется сегодня заново.

Граница суток вычисляется через `ProcessingDayProvider` в настраиваемой таймзоне
(по умолчанию UTC). Прямое обращение к `Date.now()` в application-коде запрещено: иначе
поведение на границе суток невозможно проверить тестом, а таймзона незаметно привязалась
бы к настройкам машины.

> **Найденный дефект.** Если раздел New Releases сразу давал 20 игр, цикл прерывался по
> достижении цели **до** переключения фазы, и следующий запуск снова начинал с новинок,
> где всё уже заявлено. Тест 6 это поймал. Теперь фаза переключается сразу после полного
> прохода раздела, независимо от того, достигнута ли цель.

## 6. Аренда и восстановление

```
CLAIMED (lease_until = now + WORKER_LEASE_MINUTES)
   │
   ├── воркер жив → heartbeat продлевает аренду
   │        ↓
   │     DONE / FAILED
   │
   └── воркер упал → аренда истекает
            ↓
        reaper: UPDATE той же строки → PENDING, attempts + 1
            ↓
        следующий запуск захватывает ЕЁ ЖЕ
```

**Reaper не вставляет новых строк** — только обновляет существующие. Это прямое
требование «retry без duplicate claim».

**Гонка heartbeat и reaper исключена условным продлением.**

Reaper отбирает заявки по условию `status = 'claimed' AND lease_until < now()`.
`extendLease` продлевает аренду только при выполнении **трёх** условий:

```sql
WHERE status = 'claimed'      -- заявка не завершена и не возвращена в пул
  AND lease_until > now()     -- аренда ЕЩЁ НЕ истекла
  AND run_id = $5             -- заявка принадлежит именно этому запуску
```

Проверка `lease_until > now()` — ключевая. Без неё воркер, «проспавший» истечение аренды,
воскресил бы заявку, которую reaper уже вернул в пул, и её обрабатывали бы два воркера
одновременно. Проверка `run_id` закрывает второй сценарий: заявку успел перезахватить
следующий запуск.

Метод возвращает `false`, если заявка воркеру больше не принадлежит. Воркер в этом случае
**не помечает игру завершённой** — иначе затёр бы прогресс нового владельца — и сообщает
об этом событием с категорией `lease_lost`.

Штатный запас: продление каждые `WORKER_HEARTBEAT_INTERVAL_SECONDS` (180 с) при аренде
10 минут переживает пару пропущенных срабатываний.

При `attempts >= MAX_ATTEMPTS` заявка переводится в `failed`: она перестаёт занимать место
в батче, но остаётся видимой в мониторинге.

### О статусе `processing`

Задание описывает переход `CLAIMED → PROCESSING → COMPLETED`. Отдельный статус
`processing` **не вводился**: `claimed` уже означает «захвачена и обрабатывается», а живую
работу от зависшей отличает `lease_until`. Второй статус с тем же смыслом потребовал бы
миграции данных и создал бы два источника истины о состоянии.

## 7. Пул воркеров

```
20 заявок → пул с ограничением N → N одновременных обработок
```

`Promise.all` по всему батчу не используется: 20 одновременных задач нарушили бы лимит
обращений к источнику и создали пик нагрузки на БД.

Свойства:

- **ограниченный параллелизм** — `WORKER_CONCURRENCY` (по умолчанию 4);
- **изоляция ошибок** — падение одной задачи не влияет на соседние; каждая заявка имеет
  собственный жизненный цикл, ошибка фиксируется на ней;
- **корректное освобождение** — таймер heartbeat снимается в `finally`, даже при ошибке;
- **мягкая остановка** — при отмене уже начатые задачи доводятся до конца, новые не
  запускаются и помечаются `skipped`, а не теряются молча.

Прерывать начатую работу нельзя: заявки остались бы захваченными до истечения аренды и
десять минут блокировали бы игры.

## 8. Планировщик

Планировщик **не выполняет обработку** — только инициирует запуск через
`RunDailyProcessing`. Разделение важно: он отвечает за «когда», а не за «что».

Защита от наложения запусков двухуровневая:

1. флаг выполнения внутри планировщика — не даёт запустить второй тик, пока предыдущий
   не завершён;
2. advisory lock в `RunDailyProcessing` — защищает от других процессов.

Одного `setInterval` недостаточно: он продолжает выдавать тики независимо от того,
завершилась ли предыдущая работа.

Ошибка одного тика не останавливает планировщик — следующий час может оказаться удачнее.
`stop()` дожидается уже начатого запуска.

Планировщик выключен по умолчанию (`SCHEDULER_ENABLED=false`): его включение начинает
обращения к внешнему источнику, и это должно быть осознанным решением.

## 9. Модель отказов

| Отказ | Поведение |
|---|---|
| Блокировка занята | Запуск пропускается (`run_skipped`), запись в `runs` не создаётся |
| Ошибка листинга | Поиск прекращается, уже собранные заявки обрабатываются |
| Блокировка источника (403) | Запуск завершается со статусом `blocked` — не `failed` |
| Падение обработки одной игры | Заявка → `failed`, остальные продолжаются |
| Падение воркера | Аренда истекает, reaper возвращает заявку |
| Падение процесса | Advisory lock снимается СУБД; осиротевший запуск восстанавливается (ADR-0010) |
| Источник исчерпан | Запуск завершается с частичным результатом |

Статус `blocked` отделён от `failed` намеренно: блокировка требует прекратить попытки, а
обычная ошибка — нет.

## 10. Конфигурация

| Параметр | По умолчанию | Обоснование |
|---|---|---|
| `SCHEDULER_ENABLED` | `false` | Включение начинает обращения к источнику |
| `SCHEDULER_INTERVAL_MINUTES` | `60` | Прямое требование ТЗ («1 раз в час») |
| `WORKER_CONCURRENCY` | `4` | Умеренный параллелизм; вежливость обеспечивает общий лимит запросов |
| `WORKER_LEASE_MINUTES` | `10` | Запас к целевой длительности батча (≤10 мин) |
| `WORKER_HEARTBEAT_INTERVAL_SECONDS` | `180` | Втрое чаще срока аренды — переживает пропуски |
| `MAX_PAGES_PER_RUN` | `25` | При ~24 карточках на странице хватает 2-3; запас на случай, когда почти всё заявлено |
| `MAX_EMPTY_PAGES` | `3` | Три подряд бесполезные страницы = источник исчерпан |

## 11. Наблюдаемость

События: `run_started`, `run_completed`, `run_failed`, `run_skipped`, `claim_created`,
`claim_skipped`, `claim_recovered`, `game_processing_started`,
`game_processing_completed`, `game_processing_failed`.

Запуск сохраняет `processing_day`, `source_strategy`, `last_page_hint`, `pages_scanned` —
по ним видно, к каким суткам относился проход, откуда брались кандидаты и сколько страниц
было прочитано.

В логи не попадают секреты, полный HTML и крупные полезные нагрузки: структурный логгер
вычищает чувствительные поля и обрезает длинные значения.

## Конвейер обработки игры (Phase 4)

До Phase 4 обработка одной игры сводилась к получению данных: `SyncReviewsUseCase`
и `AnalyzeReviewsUseCase` существовали, но из конвейера не вызывались. Стадия
`fetchReviews` при этом помечалась выполненной — состояние заявки не соответствовало
действительности.

Теперь последовательность стадий вынесена в `ProcessGamePipeline`
(`src/modules/ingestion/application/process-game-pipeline.ts`):

```
claim → fetchGame → fetchReviews → summarize → markDone
```

`RunDailyProcessingUseCase` отвечает за заявки, аренду и пул воркеров и вызывает
конвейер; последовательность стадий его не касается.

### Исходы стадий

| Стадия | Критичность | Исходы |
|---|---|---|
| `fetchGame` | критична | `success` \| `failed` |
| `fetchReviews` | критична | `success` \| `partial` \| `failed` |
| `summarize` | обогащающая | `success` \| `partial` \| `failed` \| `skipped` |

Правила распространения:

| Ситуация | fetchGame | fetchReviews | summarize | Итог игры |
|---|---|---|---|---|
| Всё удалось | done | done | done | `success` |
| Сбой получения данных | failed | skipped (`ingestion_failed`) | skipped | `failed` |
| Отзывы не получены | done | failed | skipped (`reviews_failed`) | `failed` |
| Неполный снимок отзывов | done | done (`incomplete_reviews`) | done | `partial` |
| Сбой разбора | done | done | failed | `partial` |
| Разбор выключен | done | done | skipped (`llm_disabled`) | `partial` |
| Хеш входа совпал | done | done | done | `success` |

`success` означает, что полностью удались ВСЕ стадии. Неполный снимок отзывов тоже
понижает исход до `partial`: разбор по нему верен лишь отчасти.

**Выключенный разбор отличим от сбоя провайдера**: `reason` равен `llm_disabled`,
а не категории ошибки. Обращения к OpenRouter при этом не происходит вовсе.

### Повторные запуски

Каждая стадия идемпотентна сама по себе, поэтому повторная обработка безопасна:

- **Данные игры** — upsert по natural key; дубликатов не возникает.
- **Отзывы** — отпечаток снимка считается по ключу и оценке (DR-4). Совпадение
  отпечатка означает пропуск записи. Изменение только текста отзыва отпечатком
  не улавливается — это осознанная оптимизация, а не дефект.
- **Разбор** — входной хеш сравнивается с сохранённым (Phase 2B). Совпадение даёт
  пропуск без обращения к модели.

### Роли процессов

`APP_ROLE` выбирает поведение единой точки входа `src/app/main.ts`:

| Роль | HTTP | Планировщик |
|---|---|---|
| `api` | да | нет |
| `worker` | нет | да |
| `all` | да | да (по умолчанию) |

Планировщик не запускается в роли `api`, чтобы несколько экземпляров не начинали
обработку одновременно. Блокировка запуска это и так предотвратила бы, но лишние
попытки ни к чему.

Ручной запуск (`POST /api/runs`) и планировщик вызывают **один и тот же**
`RunDailyProcessingUseCase`: второй реализации оркестрации нет.
