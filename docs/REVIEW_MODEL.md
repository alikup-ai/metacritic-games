# Модель отзывов и архитектура обработки

**Версия:** 1.0 (проектирование)
**Дата:** 2026-09-08
**Статус:** спроектировано; реализация не начата
**Основание:** `METACRITIC_REVIEWS_RESEARCH.md`, ADR-0012

---

## 1. Доменная модель

Два типа отзывов различаются по происхождению, идентичности и шкале оценок, поэтому
представлены раздельно, но с общей формой хранения.

```typescript
type ReviewKind = 'critic' | 'user';

/** Ключ отзыва в источнике. Форма зависит от типа — источник даёт разное. */
type ReviewIdentity =
  | { kind: 'user';   externalId: string }        // UUID источника
  | { kind: 'critic'; publicationSlug: string };  // слаг издания

interface NormalizedReview {
  readonly identity: ReviewIdentity;
  readonly platformSlug: string;

  /** critic: 0–100, user: 0–10. null допустим — встречен отзыв без оценки. */
  readonly score: number | null;
  readonly quote: string;
  readonly author: string | null;
  /** critic: может отсутствовать (3 из 93 проверенных). user: не публикуется. */
  readonly reviewUrl: string | null;
  readonly reviewDate: string | null;
  /** user: поле version источника; критерий изменения. critic: отсутствует. */
  readonly sourceVersion: number | null;
  readonly spoiler: boolean | null;
}

/** Полнота набора — отличает штатное ограничение от деградации. */
type SnapshotCompleteness = 'complete' | 'partial' | 'incomplete';

interface NormalizedReviewPage {
  readonly kind: ReviewKind;
  readonly platformSlug: string;
  readonly reviews: readonly NormalizedReview[];
  /** totalResults источника — база для вычисления полноты. */
  readonly totalAvailable: number;
  readonly completeness: SnapshotCompleteness;
  /** Записи, которые не удалось разобрать. > 0 → completeness = incomplete. */
  readonly malformed: number;
}
```

Модель не повторяет структуру ответа источника: `reviewedProduct`, `links`, `meta` и
дублирующее поле `platform` внутри записи в домен не попадают.

## 2. Стратегия идентичности

| Тип | Ключ | Основание |
|---|---|---|
| Пользовательский | `(game_id, platform_slug, external_id)` | `id` источника; проверен на 112 отзывах в двух сортировках — множества идентичны |
| Критический | `(game_id, platform_slug, publication_slug)` | `id` отсутствует; `publicationSlug` уникален 93/93 и 80/80 на двух играх |

### Почему `url` не годится для критических отзывов

Проверка всех 93 отзывов Elden Ring: 91 уникальный `url` из 93, **3 записи без URL вовсе**.
Ключ по `url` терял бы записи и схлопывал разные рецензии.

### Почему платформа обязательна

Прямое наблюдение на Witcher 3: **GameSpot и IGN** присутствуют и на PC, и на Xbox One с
одинаковой датой `2015-06-02` и одинаковой оценкой `100`. Без платформы в ключе одна из
двух рецензий была бы молча потеряна.

### Риск коллизии

Ключ критического отзыва производный. Коллизия возможна, если издание опубликует вторую
рецензию на ту же игру и платформу (переоценка после патча).

Не наблюдалась на 173 проверенных отзывах. Последствие — перезапись одной выдержки, резюме
остаётся корректным по существу. Обнаруживается по изменению `content_hash` при неизменном
ключе; предлагается логировать как сигнал.

Отвергнутая альтернатива — включить хеш текста в ключ: тогда правка опечатки создавала бы
«новый» отзыв, набор рос бы бесконечно, а fingerprint-gate перестал бы экономить вызовы LLM.

## 3. Семантика снимка

**Снимок** — состояние набора отзывов одного типа для одной платформы на момент получения.
Хранится один актуальный снимок на `(game_id, kind, platform_slug)`.

### Fingerprint

```
fingerprint = hash( sorted( ключ + ':' + score ) )
```

Считается по **отсортированному множеству ключей и оценок**, а не по сырому ответу: порядок
элементов и служебные поля меняются между запросами, и хеш ответа давал бы ложное
«изменилось» на каждом обходе, обнуляя экономию вызовов LLM (DR-4).

Совпадение fingerprint → набор не изменился → LLM не вызывается.

### Полнота

| Значение | Смысл | Удалять исчезнувшие? | Резюме |
|---|---|---|---|
| `complete` | Получены все `totalAvailable` | **Да** | Обычное |
| `partial` | Сознательное ограничение лимитом (OQ-11) | Нет | Помечено «по части отзывов» |
| `incomplete` | Обход прерван ошибкой | Нет | Помечено «данные неполны» |

Различие `partial` и `incomplete` принципиально: первое — нормальный режим экономии
запросов, второе — деградация, требующая внимания и повторного обхода.

**Инвариант: частичный снимок никогда не помечается `complete`.**

### Исчезнувшие отзывы

Признака удаления источник не даёт (RQ-2). Отзыв, отсутствующий в новом снимке, считается
исчезнувшим — но **только при `complete`**. При `partial`/`incomplete` он мог просто не
попасть в выборку.

Та же логика, что в ADR-0011: неполные данные не приводят к разрушающим действиям.

## 4. Инкрементальная обработка

```
источник (вне транзакции)
      ↓
нормализация → ключ
      ↓
классификация: новый / изменённый / неизменный / исчезнувший
      ↓
транзакция: upsert + удаление + метаданные снимка
```

| Состояние | Условие | Действие |
|---|---|---|
| новый | Ключа нет в БД | `INSERT` |
| изменённый | Ключ есть, `content_hash` отличается | `UPDATE` + `last_seen_at` |
| неизменный | Ключ есть, хеш совпал | Только `last_seen_at` |
| исчезнувший | В БД есть, в снимке нет | Удалить — **лишь при `complete`** |

Реализуется через `INSERT ... ON CONFLICT DO UPDATE` по частичному уникальному индексу.
Идемпотентность обеспечивает СУБД, а не логика приложения.

`first_seen_at` не обновляется при повторной записи — как `games.first_seen_at` в ADR-0003.

## 5. Разделение критиков и пользователей

Требование ТЗ — раздельные резюме. Обеспечено на трёх уровнях:

1. **Хранение:** колонка `kind` входит в оба уникальных индекса;
2. **Идентичность:** разные ключи; `CHECK` не даёт заполнить поле чужого типа;
3. **Снимки:** отдельная строка и свой `fingerprint` на каждый `kind`.

Следствие: сбой получения пользовательских отзывов не влияет на резюме критиков — они
обновляются, пересчитываются и деградируют независимо.

## 6. Платформа

`platform_slug` — `NOT NULL`, значение берётся из **платформы запроса** (сегмент пути), а не
из поля `platform` внутри записи: последнее дублирует контекст запроса и при обходе без
платформы показывает основную платформу игры.

**MVP обходит одну платформу** (основную). Обход всех умножает стоимость на их число и
требует отдельного решения (RQ-7). Модель готова: ключ уже содержит платформу.

**ADR-0008 в силе:** platform-specific — сами отзывы; агрегированный Userscore публикуется
общий, `userscore_scope = 'overall'` корректен. Вычислять Userscore по платформам из отзывов
и выдавать за оценку Metacritic по-прежнему нельзя.

## 7. Модель отказов

| Ситуация | Поведение | Снимок |
|---|---|---|
| Отзывов нет (200, `totalResults: 0`) | **Не ошибка** | `complete`, count = 0 |
| Игра не найдена (404) | Ошибка стадии | Не пишется |
| Источник недоступен (5xx) | Повтор HTTP-клиентом, затем ошибка | Не пишется |
| Блокировка (403) | Прекращение без повторов | Не пишется |
| Превышение лимита (429) | Ожидание по `Retry-After` | — |
| Некорректная запись | Пропуск + счётчик `malformed` | `incomplete` |
| Сбой пагинации на N-й странице | Сохранить полученное | **`incomplete`** |
| Ограничение лимитом (OQ-11) | Штатный режим | `partial` |

Отзывы — обогащающая стадия (ADR-0011): их сбой не мешает сохранению игры.

## 8. Граница транзакции

```
── ВНЕ транзакции ──
многостраничный обход источника (секунды)
── ТРАНЗАКЦИЯ ──
BEGIN
  upsert отзывов
  удаление исчезнувших (только при complete)
  сохранение метаданных снимка
COMMIT / ROLLBACK
```

Отзывы и метаданные снимка фиксируются **вместе**: иначе возможно состояние «отзывы
обновлены, fingerprint старый», при котором следующий обход счёл бы набор неизменным и не
пересчитал резюме.

## 10. Открытые вопросы

| # | Вопрос | Влияние | Предложение |
|---|---|---|---|
| RQ-1 | Меняется ли `version` при правке отзыва | Точность обнаружения изменений | Сохранять `source_version`; опираться на `content_hash` как основной критерий |
| RQ-2 | Как выглядит удалённый отзыв | Удаление исчезнувших | Считать отсутствие в `complete`-снимке признаком удаления |
| RQ-3 | Стабильны ли `id` месяцами | Долговременная идентичность | Мониторить долю «исчезнувших» |
| RQ-5 | API не документирован | **Главный риск** | Адаптер как основной путь + HTML-парсер Phase 1A как fallback |
| RQ-6 | Сколько отзывов забирать | Стоимость и качество резюме | Предлагаю: критические — все (их ≤93), пользовательские — первая страница 50 |
| RQ-7 | Обходить ли все платформы | Умножает стоимость | Предлагаю: только основную на MVP |
| **RQ-8** | Хранить ли отзывы отдельной таблицей или оставить JSONB | Объём и сложность | Предлагаю таблицу: JSONB не даёт инкрементальной обработки |

**RQ-8 — новый, требует вашего решения.** Существующая `review_snapshots.reviews JSONB`
проще, но не позволяет опознать конкретный отзыв, отследить правку и отличить новый от
изменившегося. Инкрементальная обработка (требование §3 задания) без отдельной таблицы
нереализуема. Оценка объёма: ≤50 строк на игру при лимите OQ-11, то есть порядка десятков
тысяч строк за период оценки — незначительно.
