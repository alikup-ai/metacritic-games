# Политика повторов (retry policy)

**Версия:** 1.0
**Дата:** 2026-09-07
**Статус:** действующая политика MVP

Документ фиксирует **текущую** модель повторов. Решение Product/Tech Lead: ничего не
усложнять, explicit retry внутри воркера пока не добавлять.

---

## Текущая модель

| Правило | Значение |
|---|---|
| `attempts` увеличивается | при **recovery/reaper**, не внутри воркера |
| Explicit retry внутри воркера | **не реализуется** |
| Вторая `DailyClaim` | **никогда** не создаётся |
| Повтор использует | **существующую** заявку (ту же строку) |

---

## Как это работает

### Один claim на игру в сутки

Первичный ключ `daily_claims (processing_day, source, source_slug)` делает вторую заявку
на ту же игру в те же сутки **физически невозможной**. Это не соглашение в коде, а
ограничение СУБД.

### Повтор — это UPDATE существующей строки

```
1. Воркер захватывает заявку:  status='claimed', attempts=1, lease_until=+10 мин
2. Воркер падает                (строка остаётся 'claimed' с истекающей арендой)
3. Reaper при следующем запуске: status='pending', attempts=2, run_id=NULL
                                 ^^^ UPDATE той же строки, НЕ INSERT
4. Следующий запуск захватывает: status='claimed', attempts=3
5. attempts >= MAX_ATTEMPTS  ->  status='failed'
```

На всех шагах строка одна. `attempts` растёт исключительно через путь recovery.

### Планировщик как механизм повтора

Внутри одного запуска упавшая игра **не переспрашивается**. Это осознанный выбор:
немедленный повтор при недоступности источника лишь усиливает нагрузку на него и
задерживает остальные игры батча (head-of-line blocking).

Роль механизма повтора выполняет сам почасовой график: игра, не обработанная сейчас, будет
взята следующим запуском. Дополнительный код для этого не нужен.

## Почему explicit retry внутри воркера не добавляется

1. **`attempts` перестал бы быть однозначным.** Сейчас значение означает «сколько раз
   заявка бралась в работу». При внутренних повторах пришлось бы различать два счётчика,
   иначе `MAX_ATTEMPTS` начал бы срабатывать непредсказуемо.
2. **Взаимодействие с lease.** Внутренний повтор удлиняет обработку и может пережить срок
   аренды — reaper решил бы, что воркер мёртв, и вернул бы заявку в пул **параллельно с
   продолжающейся работой**. Это привело бы к двойной обработке.
3. **Транзиентные ошибки уже покрыты уровнем ниже.** HTTP-клиент повторяет запрос при
   таймаутах, 429 и 5xx (см. `ARCHITECTURE.md` §7). Повтор на уровне элемента дублировал бы
   эту логику.

**Итог:** повторы существуют на двух уровнях — HTTP-запрос (внутри клиента) и заявка (через
recovery + следующий запуск). Промежуточный уровень намеренно отсутствует.

---

## Границы применимости

Политика распространяется на обработку игр (`daily_claims`). Она **не** относится к:

- повторам HTTP-запросов внутри клиента — своя политика (backoff + jitter, 403 без повтора);
- восстановлению осиротевших запусков — ADR-0010, счётчика попыток там нет;
- вызовам LLM — предусмотрен один повтор при невалидном структурированном ответе (Фаза 3).

---

## Условия для пересмотра

Модель придётся пересматривать, если появится любое из:

- обработка одной игры станет длиннее срока аренды (потребуется продление изнутри стадий);
- потребуется различать «ошибка источника» и «ошибка обработки» с разными лимитами;
- появится необходимость немедленного повтора для отдельного класса ошибок.

Каждый из этих случаев затрагивает взаимодействие claim/lease/reaper и потребует ADR.
