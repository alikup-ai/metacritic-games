# Ingestion — процесс получения и сохранения данных

**Версия:** 1.0
**Дата:** 2026-09-07
**Область:** Phase 1B — application-level ingestion одной игры

Документ описывает, как нормализованные данные источника попадают в каталог.
Планировщик, реестр заявок и пул воркеров сюда **не входят** — они предмет следующих фаз.

---

## 1. Поток обработки

```
MetacriticAdapter (infrastructure)
        │  реализует порт GameCatalogSource
        ▼
NormalizedGame  (доменная структура, без следов HTML)
        │
        ▼
IngestGameUseCase (application)
        │  работает ТОЛЬКО с портами
        ├──────────────► GameRepository.upsert
        ├──────────────► GamePlatformRepository.replacePlatformSnapshot
        └──────────────► IngestionEventSink.emit
        │
        ▼
PostgreSQL (infrastructure)
```

Слой application не знает про cheerio, HTML, HTTP, селекторы Metacritic и SQL. Все
зависимости выражены портами, реализации подставляются в composition root
(`src/app/bootstrap/ingestion.ts`).

### Последовательность шагов

1. Публикуется `ingestion_started`.
2. **Сеть.** `catalogSource.fetchGame()` — вне транзакции.
3. Публикуется исход по Userscore (`userscore_fetched` или `userscore_unavailable`).
4. **Транзакция:** upsert игры → синхронизация платформ → COMMIT.
5. Публикуются `game_created`/`game_updated`, `platforms_synchronized`,
   `ingestion_succeeded`.

При ошибке на любом шаге публикуется `ingestion_failed` с указанием стадии
(`fetch` или `persist`).

## 2. Граница транзакции

```
                 ── ВНЕ транзакции ──
HTTP-запрос к источнику (может длиться секунды)
                 ── НАЧАЛО транзакции ──
BEGIN
  INSERT ... ON CONFLICT (source, source_slug) DO UPDATE   -- игра
  синхронизация game_platforms                             -- платформы
COMMIT                                    (при ошибке — ROLLBACK)
```

**Почему сеть вне транзакции.** Удерживать соединение с БД на время HTTP-запроса значит
занимать пул на секунды и создавать риск таймаутов. Распределённых транзакций между
Metacritic и PostgreSQL не существует, и попытка их имитировать только вредит.

**Почему игра и платформы в одной транзакции.** Иначе возможно состояние «игра сохранена,
платформы — нет»: карточка отображалась бы без единой платформы, и отличить это от игры
без платформ было бы невозможно.

**Как это обеспечено технически.** Порт `UnitOfWork` выдаёт непрозрачный `TxContext`,
который передаётся в оба репозитория. Репозитории не открывают транзакций сами — решение
принимает вызывающий код.

> **Исправленный дефект.** В Phase 0 метод `replacePlatforms` открывал собственную
> транзакцию, из-за чего объединить его с upsert было невозможно: сбой синхронизации
> платформ оставлял сохранённую игру.

## 3. Стратегия upsert

Ключ идентичности — `(source, source_slug)`; название игры как ключ **не используется**:
у ремейков и переизданий названия совпадают.

```sql
INSERT INTO games (...) VALUES (...)
ON CONFLICT (source, source_slug) DO UPDATE SET ...
RETURNING ..., (xmax = 0) AS was_inserted
```

- `first_seen_at` **не** входит в `DO UPDATE` — дата первого появления переживает любое
  число повторных обходов.
- `xmax = 0` отличает вставку от обновления. Сравнение временных меток для этого не
  годится: они могут совпасть с точностью до микросекунд.
- `userscore_overall` обновляется через `COALESCE(EXCLUDED..., games....)` — см. §6.

## 4. Синхронизация платформ

Полная стратегия — **ADR-0011**. Кратко:

| Ситуация | Действие |
|---|---|
| Платформа в снимке, в БД нет | Создать, `is_active = TRUE` |
| Платформа в снимке и в БД | Обновить, `last_seen_at = now()` |
| Платформы нет в снимке, в БД активна | **Отключить** (`is_active = FALSE`), данные сохранить |
| Платформы нет в снимке, уже отключена | Ничего не менять |
| Отключённая платформа вернулась | Реактивировать ту же строку, без дубля |
| **Снимок пуст** | **Ничего не отключать** |

**Почему не удаляем.** Исчезновение платформы чаще означает сбой парсинга, чем реальное
снятие игры с платформы. Удаление уничтожило бы оценку безвозвратно и незаметно — ровно
тогда, когда что-то сломалось.

**Почему пустой снимок ничего не отключает.** Иначе одна поломка парсера отключила бы
платформы у всех обработанных игр за один проход. Пустой список трактуется как
«данных нет», а не «платформ больше нет».

## 5. Семантика оценок

Сохраняются четыре поля: `metascore`, `metascore_scope`, `userscore`, `userscore_scope`.

| Значение scope | Смысл |
|---|---|
| `platform` | Оценка относится именно к этой платформе (доказано для Metascore) |
| `overall` | Источник **публикует только общую** оценку. Штатное состояние для Userscore |
| `overall_fallback` | Источник, вероятно, даёт оценку по платформам, но связать **не удалось**. Деградация |
| `derived` | Рассчитана нами. На MVP не используется |

**`overall` и `overall_fallback` — разные состояния и не должны смешиваться.** Первое не
требует внимания и постоянно по объёму; рост второго — сигнал о поломке парсера. Общий
термин сделал бы деградацию невидимой.

**TBD ≠ 0.** Если оценки ещё нет, сохраняется `metascore = NULL`. Ноль означал бы
«игра оценена в 0 баллов» — фактически неверное утверждение.

**Userscore не разносится по платформам.** Metacritic не публикует его в разрезе платформ;
вычислять собственное среднее и выдавать за оценку источника запрещено (ADR-0008).

## 6. Получение Userscore

Общий Userscore требует **дополнительного** HTTP-запроса на игру, поэтому управляется
конфигурацией:

```
METACRITIC_FETCH_USERSCORE=true|false     # по умолчанию false
```

При выключенном значении ingestion работает полностью, `userscore_overall` остаётся `null`.

### Политика согласованности

Userscore классифицирован как **обогащение**:

- запрос выполняется **до** начала транзакции;
- при ошибке ingestion продолжается с `null`;
- публикуется `userscore_unavailable`.

**Обоснование:** обязательные данные (название, разработчик, платформы, Metascore) уже
получены. Отменять их сохранение из-за необязательного поля означало бы терять достоверные
данные ради недостающих необязательных.

### Защита от затирания

`null` **не перезаписывает** ранее сохранённое значение:

```sql
userscore_overall = COALESCE(EXCLUDED.userscore_overall, games.userscore_overall)
```

Без этого сбой одного запроса молча обнулял бы корректные данные, полученные ранее.

### События

| Событие | Когда |
|---|---|
| `userscore_fetched` | Значение получено |
| `userscore_unavailable` (`reason: absent`) | Источник не отдал значение |
| `userscore_unavailable` (`reason: failed`) | Запрос завершился ошибкой |
| `userscore_unavailable` (`reason: disabled`) | Догрузка выключена конфигурацией |

## 7. Политика ошибок

| Стадия | Ошибка | Последствие |
|---|---|---|
| `fetch` | Сеть, 5xx, 429 | Ingestion прерывается, записей не создаётся |
| `fetch` | 403 (блокировка) | Прерывается; повторы запрещены |
| `fetch` | Ошибка разбора | Прерывается; «успех с пустыми полями» не допускается |
| `fetch` | Userscore недоступен | **Не прерывается** — обогащение |
| `persist` | Нарушение ограничения БД | ROLLBACK, частичных данных не остаётся |
| `persist` | Обрыв соединения с БД | ROLLBACK (СУБД откатывает сама) |

Одна неудачная игра не влияет на другие: каждая обрабатывается в собственной транзакции.

---

## 8. Ответственность за повторы

На этом уровне повторов **нет** — сознательно.

| Уровень | Кто отвечает |
|---|---|
| HTTP-запрос | `MetacriticHttpClient`: backoff + jitter, 403 без повтора, 429 с `Retry-After` |
| Элемент обработки | Реестр заявок и почасовой запуск (`RETRY_POLICY.md`, следующая фаза) |
| **Ingestion игры** | **Повторов нет** — ошибка пробрасывается вызывающему |

Промежуточный уровень повторов отсутствует намеренно: он дублировал бы логику
HTTP-клиента и конфликтовал бы со сроком аренды заявки (см. `RETRY_POLICY.md`).

## 9. Гарантии идемпотентности

| Гарантия | Механизм |
|---|---|
| Повторный ingestion не создаёт вторую игру | `UNIQUE (source, source_slug)` + `ON CONFLICT` |
| Повторный ingestion не дублирует платформы | `PRIMARY KEY (game_id, platform_slug)` + `ON CONFLICT` |
| Конкурентный ingestion одной игры | Разрешается СУБД; проверено на 10 параллельных вызовах |
| Конкурентный ingestion разных игр | Независимые транзакции |
| Ошибка не оставляет частичных данных | Общая транзакция + ROLLBACK |
| Дата первого появления не теряется | `first_seen_at` вне `DO UPDATE` |
| Прежний Userscore не обнуляется | `COALESCE` при обновлении |

Идемпотентность обеспечена **ограничениями СУБД**, а не соглашениями в коде: обойти их
из приложения невозможно.

## 10. Наблюдаемость

Публикуемые события: `ingestion_started`, `ingestion_succeeded`, `ingestion_failed`,
`game_created`, `game_updated`, `platforms_synchronized`, `userscore_fetched`,
`userscore_unavailable`.

Порт `IngestionEventSink` объявлен в domain, поэтому способ доставки (лог, БД, SSE)
подменяется без изменения бизнес-логики. Реализация по умолчанию пишет в структурный лог,
который вычищает секреты и обрезает длинные значения — полный HTML и ключи туда не попадают.

Сигналы, за которыми стоит следить:

- рост `developerStatus: 'unknown'` — вероятная смена разметки;
- рост `deactivated` в `platforms_synchronized` — вероятная поломка парсера платформ;
- `skippedDeactivation: true` — источник вернул пустой список платформ.
