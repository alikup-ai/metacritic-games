# ADR-0004: Claim / Lease / Recovery для идемпотентной обработки

**Статус:** Принято
**Дата:** 2026-09-07
**Решение принял:** Product/Tech Lead
**Связано с:** OQ-13

---

## Контекст

Решение Tech Lead по OQ-13 задаёт жёсткие требования:

- «20 games» = 20 уникальных игр, успешно **CLAIMED** в рамках processing day.
- Claim обязан быть **идемпотентным**.
- Повторный запуск **не должен** повторно claim одну и ту же игру в тот же processing day.
- Failed processing после claim обязан иметь retry/recovery через **lease/reaper**,
  **не создавая duplicate claim**.

Плюс требование корректного поведения после: перезапуска приложения, падения worker,
повторного запуска job, параллельного запуска workers, частично завершённой обработки.

## Рассмотренные варианты

### A. Проверить-затем-вставить (`SELECT` → `INSERT`)
- ❌ Гонка: два воркера видят «свободно» и оба вставляют. Классический TOCTOU.

### B. Блокировка таблицы на время планирования
- ➕ Корректно.
- ➖ Сериализует планирование, блокирует конкурентов, плохо масштабируется.

### C. Атомарный `INSERT ... ON CONFLICT DO NOTHING` + lease + reaper (выбрано)
- ➕ Атомарность на уровне строки, гонки исключены СУБД.
- ➕ Идемпотентность — прямое следствие ограничения уникальности.
- ➕ Lease решает проблему упавшего воркера.
- ➖ Требует фонового reaper и настройки таймаута lease.

### D. Внешняя очередь (Redis/BullMQ)
- ➕ Готовые механизмы повторов.
- ➖ Дополнительный компонент инфраструктуры ради ~20 задач в час.
- ➖ Противоречит решению «без избыточной инфраструктуры» (OQ-15).

## Решение

Принят **вариант C**.

### Фаза 1 — CLAIM (атомарно и идемпотентно)

```sql
INSERT INTO daily_claim (day, source, source_slug, run_id, status,
                         lease_expires_at, attempts)
VALUES ($1, $2, $3, $4, 'claimed', now() + $5::interval, 1)
ON CONFLICT (day, source, source_slug) DO NOTHING
RETURNING *;
```

- Вернулась строка → игра захвачена этим воркером.
- Пусто → игра уже захвачена или обработана сегодня → пропустить.

Первичный ключ `(day, source, source_slug)` делает физически невозможным двойной claim одной
игры в одни сутки — ровно то, что требует OQ-13. Идемпотентность обеспечивается СУБД, а не
логикой приложения.

### Фаза 2 — Обработка со стадийным сохранением

Каждая завершённая стадия немедленно фиксируется в `stages JSONB`:

```json
{ "fetchGame": "done", "fetchReviews": "done", "summarize": "pending" }
```

Пока воркер жив, он продлевает lease. При повторной обработке выполненные стадии
пропускаются — частично выполненная работа не теряется.

### Фаза 3 — Завершение

```sql
UPDATE daily_claim
SET status = 'done', lease_expires_at = NULL, stages = $2
WHERE day = $1 AND source = $3 AND source_slug = $4;
```

### Reaper — восстановление после падения воркера

Запускается в начале каждого run:

```sql
UPDATE daily_claim
SET status = 'pending', attempts = attempts + 1, lease_expires_at = NULL
WHERE status = 'claimed' AND lease_expires_at < now();
```

**Ключевой момент:** reaper **обновляет существующую строку**, а не вставляет новую.
Требование «retry без duplicate claim» выполняется буквально.

При `attempts >= max_attempts` claim переводится в `failed`: игра перестаёт занимать место в
батче, но остаётся видимой в мониторинге для разбора.

### Зачем нужен lease

Без lease упавший воркер оставил бы игру в статусе `claimed` навсегда, и она **молча** не
обрабатывалась бы в этот день. Это отказ, который выглядит как нормальная работа — самый
опасный класс ошибок в подобных системах. Lease делает его самовосстанавливающимся.

## Матрица гарантий

| Сценарий | Гарантия | Механизм |
|---|---|---|
| Перезапуск приложения | Нет дублей и потерь | Состояние в PostgreSQL; advisory lock снимается СУБД при разрыве сессии; план пересчитывается из БД |
| Падение worker | Игра повторно обработана | Просроченный lease → reaper возвращает в пул, `attempts++` |
| Повторный запуск job | Безопасен | `ON CONFLICT DO NOTHING` + upsert игры |
| Параллельные workers | Нет двойной обработки | Атомарный claim: побеждает ровно один |
| Частичная обработка | Продолжает, не начинает заново | Стадии в `stages`, выполненные пропускаются |

## Уровни конкурентности

1. **Run:** advisory lock PostgreSQL — не более одного запуска глобально (защита от
   коллизии cron и Force Run). Lock сессионный → освобождается СУБД при падении процесса.
2. **Элемент:** пул воркеров (4), безопасен благодаря атомарному claim.
3. **Сеть:** общий token bucket ≤1 req/s. Вежливость не зависит от числа воркеров.

## Последствия

**Положительные**
- Все пять сценариев отказа из ТЗ покрыты явными механизмами.
- Идемпотентность гарантирована СУБД, а не соглашениями в коде.
- Нет внешней очереди — соответствует «без избыточной инфраструктуры».

**Отрицательные**
- Нужно подобрать таймаут lease: слишком мал → двойная обработка живой игры;
  слишком велик → медленное восстановление. Стартовое значение — 10 минут
  (при целевой длительности батча ≤10 минут), с продлением активным воркером.

## Проверяемость

- Тест: параллельный claim одного слага двумя воркерами → успешен ровно один.
- Тест: повторный запуск в тот же день не создаёт второй claim.
- Тест: убитый воркер → после истечения lease игра возвращается в пул.
- Тест: перезапуск после части стадий → продолжение, а не начало заново.
