# ADR-0001: Модульный монолит с разделением domain/application/infrastructure

**Статус:** Принято
**Дата:** 2026-09-07
**Решение принял:** Product/Tech Lead
**Связано с:** OQ-2

---

## Контекст

Требуется сервис, объединяющий несколько разнородных задач: периодический scraping,
фоновая обработка, LLM-обогащение, веб-интерфейс и realtime-мониторинг. Нужно выбрать
стиль архитектуры и способ изоляции внешних зависимостей.

Ограничения:
- Результат тестового задания должен быть **работающим сервисом по ссылке** — простота
  развёртывания напрямую влияет на оценку.
- Объём нагрузки мал: 20 игр в час, десятки запросов.
- Внешние зависимости (Metacritic, LLM, YouTube) нестабильны и могут меняться.
- Требование Tech Lead: доменные модули не должны зависеть напрямую от
  infrastructure/external providers.

## Рассмотренные варианты

### A. Модульный монолит с domain/application/infrastructure (выбрано)
Один деплой, внутренние границы модулей, внешние интеграции за портами.

- ➕ Один деплой, `docker compose up` — прямо служит требованию «живая ссылка».
- ➕ Границы модулей сохраняют возможность выделения сервисов позже.
- ➕ Порты изолируют нестабильные внешние API: смена провайдера = один адаптер.
- ➕ Транзакционная целостность без распределённых транзакций.
- ➖ Требует дисциплины: без автоматической проверки слои «протекают».

### B. Микросервисы (scraper / api / worker раздельно)
- ➕ Независимое масштабирование.
- ➖ Несоразмерно нагрузке: инфраструктуры больше, чем полезной логики.
- ➖ Усложняет развёртывание демо, добавляет сетевые режимы отказа.
- ➖ Распределённая трассировка ради 20 игр в час не окупается.
- ❌ **Прямо запрещено** решением Tech Lead.

### C. Монолит без слоёв («всё в сервисах»)
- ➕ Быстрый старт.
- ➖ Бизнес-логика смешивается с HTTP и SQL, тестируется только с БД и сетью.
- ➖ Смена LLM-провайдера или редизайн Metacritic задевают всю кодовую базу.

## Решение

Принят **вариант A**.

Слои и правила зависимостей:

```
domain          → без внешних зависимостей (чистый TypeScript)
application     → зависит только от domain
infrastructure  → реализует порты, объявленные в domain
app             → composition root: связывает всё вместе
```

Модули: `catalog`, `ingestion`, `reviews`, `similarity`, `video`, `monitoring`.
Межмодульное взаимодействие — только через application-слой.

Порты в domain: `GameCatalogSource`, `ReviewSource`, `LlmProvider`, `VideoProvider`,
`TranscriptProvider`, `GameRepository`, `ClaimRepository`, `RunRepository`.

## Последствия

**Положительные**
- Доменные правила (день-план, claim/lease, идентичность) тестируются юнит-тестами без БД
  и сети — это самая ценная для проверки часть системы.
- Отключение YouTube по feature flag тривиально: адаптер просто не подключается.
- Замена LLM-провайдера не затрагивает бизнес-логику.

**Отрицательные / издержки**
- Больше файлов и явного маппинга, чем при «плоском» подходе.
- Нужна автоматическая проверка границ, иначе правила размоются.

**Митигация:** `dependency-cruiser` в CI запрещает импорты `infrastructure` из `domain`.
Нарушение = падение сборки, а не замечание на code review.

## Проверяемость

- CI падает при нарушении правил зависимостей.
- Доменные тесты выполняются без PostgreSQL и без сети.
