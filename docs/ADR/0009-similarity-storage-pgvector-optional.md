# ADR-0009: Хранение схожести с опциональной поддержкой pgvector

**Статус:** Принято
**Дата:** 2026-09-07
**Связано с:** OQ-12

---

## Контекст

ТЗ требует подбирать похожие игры из уже имеющихся в базе. Требование к проектированию:
предусмотреть возможность pgvector, но **не делать vector search обязательным для запуска
миграций**, если это усложняет развёртывание, и предложить простой fallback.

Ограничение развёртывания: `docker compose up` на VPS должен работать без ручной установки
расширений. Образ `postgres:16` не содержит pgvector — потребовался бы кастомный образ
(`pgvector/pgvector`), что усложняет и утяжеляет деплой ради функции, не входящей в MVP.

## Рассмотренные варианты

### A. Обязательный pgvector с самого начала
- ➕ Готовность к семантическому поиску.
- ➖ Кастомный образ PostgreSQL, миграции падают без расширения.
- ➖ Усложняет развёртывание ради неиспользуемой на MVP возможности.
- ❌ Противоречит требованию «не делать обязательным для миграций».

### B. Только content-based, без задела (выбрано как база)
- ➕ Простое развёртывание, стандартный образ.
- ➖ Переход на эмбеддинги потребует миграции схемы.

### C. Content-based + условная поддержка pgvector (выбрано)
- ➕ Стандартный образ, миграции не зависят от расширения.
- ➕ Эмбеддинги добавляются позже без переписывания.
- ➖ Немного больше логики в миграции.

## Решение

Принят **вариант C**.

### 1. Хранение результата не зависит от метода

```sql
similar_games (
  game_id         UUID NOT NULL,
  similar_game_id UUID NOT NULL,
  score           REAL NOT NULL,     -- 0..1
  method          TEXT NOT NULL,     -- 'content_v1' | 'embedding_v1'
  computed_at     TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (game_id, similar_game_id)
)
```

Поле `method` фиксирует, чем посчитана связь. Смена алгоритма — это новые строки с другим
`method`, а не миграция схемы. Можно держать оба результата одновременно и сравнивать.

### 2. Алгоритм MVP — content-based

Взвешенная сумма: совпадение жанров, пересечение платформ, совпадение
developer/publisher, trigram-схожесть названия. Детерминирован, бесплатен, объясним.

Требуется `pg_trgm` — расширение из состава `postgres-contrib`, **входит в стандартный
образ**, ставится через `CREATE EXTENSION IF NOT EXISTS pg_trgm`. В отличие от pgvector,
дополнительного образа не требует.

### 3. pgvector — опционально и безопасно

Миграция эмбеддингов **не падает** при отсутствии расширения:

```sql
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM pg_available_extensions WHERE name = 'vector') THEN
    CREATE EXTENSION IF NOT EXISTS vector;
    CREATE TABLE IF NOT EXISTS game_embeddings (
      game_id   UUID PRIMARY KEY REFERENCES games(id) ON DELETE CASCADE,
      embedding vector(1536) NOT NULL,
      model     TEXT NOT NULL,
      created_at TIMESTAMPTZ NOT NULL DEFAULT now()
    );
  ELSE
    RAISE NOTICE 'pgvector недоступен — семантический поиск отключён, используется content_v1';
  END IF;
END $$;
```

Приложение при старте определяет доступность расширения и выбирает стратегию. Отсутствие
pgvector — штатный режим, а не ошибка.

### Почему не хранить эмбеддинги в `REAL[]`

Массив работал бы без расширения, но без индекса поиск ближайших соседей деградирует до
полного перебора. Это создало бы иллюзию поддержки семантического поиска при негодной
производительности. Честнее: либо pgvector с индексом, либо content-based.

## Последствия

**Положительные**
- `docker compose up` работает на стандартном `postgres:16`.
- Миграции не зависят от наличия расширения.
- Переход на эмбеддинги не требует изменения схемы результатов.

**Отрицательные**
- Условная логика в миграции (одна `DO`-конструкция).
- На MVP семантической схожести нет — принято осознанно.

## Проверяемость

- Тест: миграции применяются на стандартном `postgres:16` без ошибок.
- Тест: `pg_trgm` создаётся успешно.
- Тест: отсутствие pgvector не роняет миграцию (только NOTICE).
- Тест: `similar_games` заполняется с `method='content_v1'`.
