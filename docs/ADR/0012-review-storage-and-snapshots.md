# ADR-0012: Хранение отзывов и модель снимков

**Статус:** Принято (проектирование; реализация не начата)
**Дата:** 2026-09-08
**Основание:** `docs/METACRITIC_REVIEWS_RESEARCH.md`
**Связано с:** ADR-0003 (идентичность), ADR-0008 (семантика оценок), ADR-0011 (снимки платформ)

---

## Контекст

ТЗ требует отдельных резюме по отзывам критиков и пользователей, с возможностью обновления
при повторных обходах. Отсюда три задачи: устойчиво опознавать отзыв, отличать изменившийся
набор от неизменного и не создавать дубликатов при повторной обработке.

Исследование установило факты, которые определяют модель:

| Факт | Следствие |
|---|---|
| У пользовательских отзывов есть `id` (UUID), стабильный между запросами | Готовый внешний ключ |
| У критических отзывов `id` **отсутствует** | Нужен составной ключ |
| Оба типа platform-specific (платформа — сегмент пути) | Платформа входит в модель |
| Агрегированный Userscore публикуется общий | ADR-0008 не меняется |
| `limit` у критических игнорируется (всегда 10) | Обход дороже, чем кажется |
| Отсутствие отзывов — HTTP 200, а не ошибка | Пустой результат валиден |

## Часть 1 — Идентичность отзыва

### Пользовательские отзывы: внешний ID

Источник даёт `id` вида `ad709db3-0a82-4cb5-ad6b-d554ca40bfac`.

**Проверено:** на игре со 112 отзывами полная выборка в двух сортировках (`date`, `score`)
дала идентичные множества `id`, а у одного и того же `id` совпали `quote`, `score`, `date`,
`author`, `version`. На 100 проверенных отзывах поле заполнено везде.

```
Ключ: (game_id, platform, external_id)
```

Платформа входит в ключ, потому что endpoint платформо-зависимый: один и тот же
пользователь может оставить отзывы на разных платформах.

### Критические отзывы: составной ключ

`id` отсутствует. Проверены три кандидата на всех 93 отзывах Elden Ring и всех 80 отзывах
Witcher 3:

| Кандидат | Результат | Пригодность |
|---|---|---|
| `url` | 91 уникальных из 93; **3 записи вообще без URL** | ❌ |
| `publicationSlug` | **93 из 93** и **80 из 80** уникальны | ✅ |
| `publicationSlug` + `date` | Уникален | Избыточно |

```
Ключ: (game_id, platform, publication_slug)
```

### Почему платформа обязательна в ключе

Прямая проверка: **GameSpot и IGN рецензировали Witcher 3 и на PC, и на Xbox One**, с
одинаковой датой (`2015-06-02`) и одинаковой оценкой (100).

```
PC/gamespot        → 2015-06-02, score 100
xbox-one/gamespot  → 2015-06-02, score 100
```

Без платформы в ключе эти две записи схлопнулись бы в одну, и рецензия на одну из платформ
была бы молча потеряна. Ключ `(game_id, publication_slug)` **непригоден**.

### Риск коллизии составного ключа

Ключ производный, а не выданный источником. Коллизия наступит, если издание опубликует
**вторую** рецензию на ту же игру и платформу — например, переоценку после патча.

| Аспект | Оценка |
|---|---|
| Наблюдалась ли | Нет: 173 проверенных отзыва на двух играх, дублей нет |
| Вероятность | Низкая — модель Metacritic «одно издание = одна рецензия на платформу» |
| Последствие | Вторая рецензия перезапишет первую |
| Ущерб | Потеря одной выдержки; резюме останется корректным по существу |
| Обнаружение | Изменение `content_hash` при неизменном ключе — можно логировать |

**Принято осознанно.** Альтернатива — хеш от текста в ключе — сделала бы правку опечатки в
выдержке новым отзывом, что хуже: набор рос бы бесконечно, а fingerprint-gate перестал бы
экономить вызовы LLM.

## Часть 2 — Модель снимка

### Существующая таблица сохраняется

`review_snapshots` из Phase 0 уже содержит нужное: `kind` (critic/user), `fingerprint`,
`review_count`, `truncated`, `fetched_at`, ограничение `UNIQUE (game_id, kind)`.

**Переписывать её не требуется.** Нужны три уточнения, оформляемые отдельной миграцией:

```sql
ALTER TABLE review_snapshots
    ADD COLUMN platform_slug TEXT,          -- отзывы platform-specific
    ADD COLUMN completeness TEXT NOT NULL DEFAULT 'complete',
    ADD COLUMN total_available INTEGER;     -- totalResults источника
```

и замена ограничения уникальности:

```sql
UNIQUE (game_id, kind, platform_slug)
```

### Что такое снимок

Снимок — **состояние набора отзывов одного типа для одной платформы на момент получения**.
Хранится один актуальный снимок на `(game_id, kind, platform_slug)`; история версий не
ведётся (retention, `RETENTION_POLICY.md`).

### Что считается новой версией

Сравнивается `fingerprint` — хеш от **отсортированного множества ключей отзывов и их
оценок**, а не от сырого JSON:

```
fingerprint = hash( sorted( [key(review) + ':' + score] ) )
```

Почему не хеш ответа целиком: порядок элементов и служебные поля (`links`, `meta`) меняются
между запросами, и хеш сырого ответа давал бы ложное «изменилось» на каждом обходе,
обнуляя экономию вызовов LLM (DR-4).

- `fingerprint` совпал → набор не изменился, LLM не вызывается;
- `fingerprint` отличается → снимок обновляется, резюме пересчитывается.

### Как отличить частичный снимок от полного

Это прямое требование задания: **частично полученный снимок не должен выглядеть полным.**

```
completeness:
  'complete'    — получены все отзывы (review_count == total_available)
  'partial'     — сознательно ограничено лимитом (OQ-11)
  'incomplete'  — обход прерван ошибкой; данные неполны НЕПРЕДНАМЕРЕННО
```

Различие между `partial` и `incomplete` существенно: первое — нормальный режим экономии
запросов, второе — деградация, на которую нужно реагировать. Существующее поле `truncated`
покрывало только первый случай.

**Правило:** резюме по снимку со статусом `incomplete` помечается как построенное по
неполным данным, а `fingerprint` такого снимка **не считается основанием пропустить**
следующий обход.

### Исчезнувшие отзывы

Признака удаления источник не даёт (RQ-2). Отзыв, отсутствующий в новом полном снимке,
считается исчезнувшим и удаляется из набора.

**Но только при `completeness = 'complete'`.** Для `partial` и `incomplete` отсутствие
отзыва не означает удаления — он мог просто не попасть в выборку. Это та же логика, что в
ADR-0011: пустой снимок не отключает платформы.

## Часть 3 — Хранение отзывов

### Отдельная таблица вместо JSONB-массива

Существующая `review_snapshots.reviews JSONB` хранит набор одним блобом. Для инкрементальной
обработки этого недостаточно: нельзя опознать конкретный отзыв, отследить изменение его
текста и отличить новый от изменившегося.

```sql
CREATE TABLE reviews (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    game_id         UUID NOT NULL REFERENCES games (id) ON DELETE CASCADE,
    kind            TEXT NOT NULL,               -- 'critic' | 'user'
    platform_slug   TEXT NOT NULL,

    -- Идентичность источника: ровно одно из двух заполнено
    external_id     TEXT,                        -- user: UUID источника
    publication_slug TEXT,                       -- critic: слаг издания

    score           SMALLINT,                    -- NULL допустим: встречен отзыв без оценки
    quote           TEXT NOT NULL,
    author          TEXT,
    review_url      TEXT,                        -- critic: может отсутствовать (3 из 93)
    review_date     DATE,
    source_version  BIGINT,                      -- user: поле version источника
    spoiler         BOOLEAN,

    content_hash    TEXT NOT NULL,               -- обнаружение правки текста
    first_seen_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_seen_at    TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT reviews_kind_valid CHECK (kind IN ('critic', 'user')),
    -- Ключ источника обязателен и соответствует типу отзыва
    CONSTRAINT reviews_identity_valid CHECK (
        (kind = 'user'   AND external_id IS NOT NULL AND publication_slug IS NULL)
     OR (kind = 'critic' AND publication_slug IS NOT NULL AND external_id IS NULL)
    ),
    CONSTRAINT reviews_score_range CHECK (
        score IS NULL
     OR (kind = 'critic' AND score BETWEEN 0 AND 100)
     OR (kind = 'user'   AND score BETWEEN 0 AND 10)
    )
);

-- Два частичных уникальных индекса вместо одного общего: ключи разных типов
-- лежат в разных колонках, и общий индекс по обеим допускал бы NULL-дыры.
CREATE UNIQUE INDEX reviews_user_identity_idx
    ON reviews (game_id, platform_slug, external_id)
    WHERE kind = 'user';

CREATE UNIQUE INDEX reviews_critic_identity_idx
    ON reviews (game_id, platform_slug, publication_slug)
    WHERE kind = 'critic';

CREATE INDEX reviews_game_kind_idx ON reviews (game_id, kind, platform_slug);
```

Шкалы оценок различаются (критики 0–100, пользователи 0–10) — ограничение это учитывает.
`score` nullable: в выборке встретился критический отзыв без оценки.

`review_snapshots` при этом сохраняется как **метаданные набора** (fingerprint, полнота,
счётчики), а не как хранилище самих отзывов.

## Часть 4 — Разделение критиков и пользователей

Смешивать нельзя: ТЗ требует раздельных резюме.

Разделение обеспечивается на трёх уровнях:

1. **Хранение** — колонка `kind`, входящая в оба уникальных индекса;
2. **Идентичность** — разные ключи (`external_id` против `publication_slug`), а
   `CHECK`-ограничение не даёт заполнить чужое поле;
3. **Снимки** — отдельная строка `review_snapshots` на каждый `kind`, свой `fingerprint`.

Следствие: критические и пользовательские отзывы обновляются, пересчитываются и деградируют
**независимо**. Сбой получения пользовательских отзывов не влияет на резюме критиков.

## Часть 5 — Платформа

Исследование доказало платформенную привязку обоих типов, поэтому `platform_slug`
включается в модель как **NOT NULL**.

Значение берётся из платформы, для которой выполнялся запрос (сегмент пути), а не из поля
`platform` внутри записи: оно дублирует контекст запроса и при обходе без платформы
показывает основную платформу игры, а не реальную платформу рецензии.

**На MVP обходится только одна платформа** (основная — endpoint без сегмента). Обход всех
платформ умножает стоимость на их число и требует отдельного продуктового решения (RQ-7).
Модель к этому готова: ключ уже содержит платформу, добавление второй платформы не потребует
миграции.

**ADR-0008 не отменяется.** Platform-specific — сами отзывы; агрегированный Userscore
по-прежнему публикуется общий, и `userscore_scope = 'overall'` остаётся верным. Вычислять
Userscore по платформе из отзывов и выдавать за оценку Metacritic по-прежнему запрещено.

## Часть 6 — Инкрементальная обработка

```
источник → нормализация → ключ → классификация → снимок
```

Классификация каждого отзыва по ключу:

| Состояние | Условие | Действие |
|---|---|---|
| **новый** | Ключа нет в БД | `INSERT` |
| **изменённый** | Ключ есть, `content_hash` отличается | `UPDATE`, обновить `last_seen_at` |
| **неизменный** | Ключ есть, хеш совпал | Обновить только `last_seen_at` |
| **исчезнувший** | Ключ в БД есть, в снимке нет | Удалить — **только при `complete`** |

Реализуется одним `INSERT ... ON CONFLICT DO UPDATE` по частичному уникальному индексу.
Идемпотентность обеспечивает СУБД, а не логика приложения — как в ADR-0004 и ADR-0011.

Повторная обработка той же игры не создаёт дубликатов: ключ стабилен, конфликт разрешается
обновлением.

## Часть 7 — Порты

Три порта, без лишних абстракций:

```typescript
// domain
interface ReviewSource {
  fetchReviews(params: {
    sourceSlug: string;
    kind: 'critic' | 'user';
    platform?: string;
    limit?: number;
    signal?: AbortSignal;
  }): Promise<NormalizedReviewPage>;
}

interface ReviewRepository {
  upsertMany(gameId, kind, platform, reviews, tx?): Promise<ReviewSyncResult>;
  findByGame(gameId, kind, platform, tx?): Promise<readonly StoredReview[]>;
  deleteMissing(gameId, kind, platform, presentKeys, tx?): Promise<number>;
}

interface ReviewSnapshotRepository {
  findSnapshot(gameId, kind, platform, tx?): Promise<ReviewSnapshot | null>;
  saveSnapshot(snapshot, tx?): Promise<void>;
}
```

Отдельный `ReviewSnapshotRepository` оправдан: снимок — метаданные набора с собственным
жизненным циклом (fingerprint, полнота), а не строка отзыва. Объединение в один порт
смешало бы два разных понятия.

`NormalizedReviewPage` возвращает `totalAvailable` и `completeness` — из них строится
статус снимка.

## Часть 8 — Граница транзакции

Та же схема, что в ADR-0011:

```
── ВНЕ транзакции ──
получение отзывов (может быть несколько страниц, секунды)
── ТРАНЗАКЦИЯ ──
BEGIN
  upsert reviews
  удаление исчезнувших (только при completeness = 'complete')
  сохранение метаданных снимка
COMMIT                            (при ошибке — ROLLBACK)
```

Сеть вне транзакции: удерживать соединение с БД на время многостраничного обхода
недопустимо. Отзывы и метаданные снимка фиксируются вместе — иначе возможно состояние
«отзывы обновлены, fingerprint старый», при котором следующий обход счёл бы набор
неизменным и не пересчитал резюме.

## Часть 9 — Модель отказов

| Ситуация | Поведение | Снимок |
|---|---|---|
| Отзывов нет (HTTP 200, `totalResults: 0`) | **Не ошибка** | `complete`, `review_count = 0` |
| Игра не найдена (404) | Ошибка стадии | Снимок не пишется |
| Источник недоступен (5xx) | Повтор HTTP-клиентом; при исчерпании — ошибка стадии | Не пишется |
| Блокировка (403) | Прекращение без повторов | Не пишется |
| Превышение лимита (429) | Ожидание по `Retry-After` | — |
| Некорректная запись в ответе | Пропустить запись, счётчик в лог | `incomplete` |
| Сбой пагинации на N-й странице | Сохранить полученное | **`incomplete`** |
| Ограничение по лимиту (OQ-11) | Штатный режим | `partial` |

Ключевое правило: **частичный снимок никогда не помечается `complete`**. Из этого следует:

- исчезнувшие отзывы не удаляются;
- резюме помечается как построенное по неполным данным;
- `fingerprint` не блокирует следующий обход.

Отзывы — обогащающая стадия (ADR-0011): их сбой не влияет на сохранение самой игры.

## Последствия

**Положительные**
- Идемпотентность обеспечена ограничениями СУБД.
- Критики и пользователи независимы на всех уровнях.
- Частичные данные отличимы от полных — резюме не вводит в заблуждение.
- Существующая `review_snapshots` сохранена, изменения аддитивны.

**Отрицательные**
- Составной ключ критических отзывов производный; риск описан и принят.
- Новая таблица `reviews` увеличивает объём: до ~50 строк на игру при лимите OQ-11.
- Обход одной платформы означает неполный охват мультиплатформенных игр — осознанное
  ограничение MVP.

## Проверяемость

Полный перечень — в `REVIEW_MODEL.md`, §9. Ключевые:

- повторная обработка не создаёт дубликатов;
- одно издание на двух платформах даёт **две** строки;
- изменение текста обновляет строку, а не создаёт новую;
- исчезнувший отзыв удаляется при `complete` и **сохраняется** при `incomplete`;
- сбой пагинации даёт `incomplete`, а не `complete`;
- ошибка в транзакции не оставляет частичных данных.
