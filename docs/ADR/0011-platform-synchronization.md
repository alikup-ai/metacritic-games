# ADR-0011: Синхронизация платформ и граница транзакции при ingestion

**Статус:** Принято
**Дата:** 2026-09-07
**Связано с:** ADR-0003, ADR-0008

---

## Контекст

При повторной обработке игры набор платформ может измениться: платформа добавляется,
меняется её оценка или платформа исчезает из источника. Требование Product/Tech Lead:
**исчезнувшую платформу не удалять молча**.

Обнаруженный дефект в реализации Phase 0: метод `replacePlatforms` выполнял
`DELETE` + `INSERT`, то есть физически удалял платформы, и делал это в **собственной**
транзакции, из-за чего upsert игры и синхронизацию платформ нельзя было объединить
в один атомарный блок.

## Часть 1 — Что делать с исчезнувшей платформой

### Рассмотренные варианты

**A. Физическое удаление (было).**
- ➕ Простейшая реализация.
- ❌ Исчезновение платформы чаще означает сбой парсинга или временное изменение вёрстки,
  а не реальное снятие игры с платформы. Удаление уничтожает оценку безвозвратно и
  незаметно — данные теряются именно тогда, когда что-то сломалось.

**B. Отдельная таблица снимков (source snapshot).**
- ➕ Полная история изменений источника.
- ➖ Требует версионирования, усложняет все выборки и миграции ради данных, которые на
  MVP никто не читает.

**C. Active/inactive — мягкое отключение (выбрано).**
- ➕ Одна булева колонка; данные сохраняются полностью.
- ➕ Обратимо: вернувшаяся платформа снова становится активной.
- ➕ Объяснимо в UI: показываем активные, при желании — «больше не указана источником».
- ➕ Рост числа неактивных платформ — наблюдаемый сигнал о поломке парсера.
- ➖ Выборки обязаны фильтровать по `is_active`.

### Решение

Принят **вариант C**.

```sql
is_active      BOOLEAN NOT NULL DEFAULT TRUE
last_seen_at   TIMESTAMPTZ NOT NULL DEFAULT now()
deactivated_at TIMESTAMPTZ            -- NULL пока активна
```

Ограничение целостности не даёт рассогласовать флаг и дату:

```sql
CHECK ((is_active AND deactivated_at IS NULL)
    OR (NOT is_active AND deactivated_at IS NOT NULL))
```

### Правила синхронизации снимка

| Ситуация | Действие |
|---|---|
| Платформа есть в снимке, в БД её нет | `INSERT`, `is_active = TRUE` |
| Платформа есть и в снимке, и в БД | `UPDATE` полей, `last_seen_at = now()`, реактивация при необходимости |
| Платформы нет в снимке, в БД активна | `is_active = FALSE`, `deactivated_at = now()`. **Данные сохраняются** |
| Платформы нет в снимке, в БД уже неактивна | Ничего — `deactivated_at` не переписывается |
| **Снимок пуст** | **Ничего не отключается** (см. ниже) |

### Защита от каскадного отключения

Пустой список платформ трактуется как **отсутствие данных**, а не как «платформ больше
нет». Иначе одна поломка парсера отключила бы платформы у всех обработанных игр за один
проход — тихая порча каталога.

Отключение выполняется только тогда, когда снимок непуст, то есть источник заведомо
отдал осмысленные данные.

## Часть 2 — Граница транзакции

### Решение

```
1. Получить данные из источника (HTTP) — ВНЕ транзакции
2. BEGIN
3.   upsert games
4.   синхронизировать game_platforms
5. COMMIT   (при ошибке — ROLLBACK)
```

Ключевые свойства:

- **Сеть за пределами транзакции.** Медленный HTTP-запрос не удерживает соединение с БД
  и не порождает распределённых транзакций.
- **Игра и её платформы фиксируются вместе.** Промежуточное состояние «игра сохранена,
  платформы — нет» невозможно.
- **Один клиент на всю операцию.** Репозитории принимают исполнителя запросов
  (`QueryExecutor`), поэтому вызывающий код решает, выполняются ли операции в общей
  транзакции. Прежняя реализация открывала транзакцию внутри себя и такой возможности
  не давала.

### Политика согласованности для Userscore

Общий Userscore требует **дополнительного** HTTP-запроса. Он классифицирован как
обогащение:

- запрос выполняется **до** начала транзакции;
- при ошибке ingestion продолжается с `userscoreOverall = null`;
- факт неудачи фиксируется отдельным событием (`userscore_unavailable`).

Обоснование: обязательные данные (название, разработчик, платформы, Metascore) уже
получены. Отменять их сохранение из-за необязательного поля означало бы терять
достоверные данные ради недостающего необязательного.

При этом `null` **не затирает** ранее сохранённое значение: если Userscore был получен
вчера, а сегодня запрос не удался, прежнее значение сохраняется (`COALESCE` при upsert).
Иначе сбой одного запроса молча обнулял бы корректные данные.

## Последствия

**Положительные**
- Данные не теряются при сбоях парсинга.
- Игра и платформы всегда согласованы.
- Отключения платформ наблюдаемы и обратимы.

**Отрицательные**
- Все выборки платформ обязаны учитывать `is_active`; забытый фильтр покажет устаревшие
  данные. Митигация — активные платформы возвращаются отдельным методом репозитория.
- Неактивные строки накапливаются. Объём незначителен (единицы на игру), очистка при
  необходимости выносится в production hardening.

## Проверяемость

- Тест: исчезнувшая платформа отключается, а не удаляется; её оценка сохраняется.
- Тест: вернувшаяся платформа снова активируется.
- Тест: пустой снимок ничего не отключает.
- Тест: ошибка внутри транзакции не оставляет частично сохранённых данных.
- Тест: неудача Userscore не отменяет сохранение игры и не затирает прежнее значение.
