# ADR-0010: Критерий и восстановление осиротевших запусков (orphaned runs)

**Статус:** Принято
**Дата:** 2026-09-07
**Основание:** риск, выявленный при реализации database foundation

---

## Контекст

Уникальный частичный индекс `runs_single_active_idx` допускает не более одной строки
`runs` со статусом `running`. Это второй барьер против параллельных запусков в дополнение
к advisory lock.

**Обнаруженная проблема.** При аварийном завершении процесса (kill, OOM, перезагрузка
хоста) строка остаётся в статусе `running` навсегда:

- advisory lock снимается СУБД автоматически при обрыве сессии — **проверено**;
- строка `runs` не откатывается, так как транзакция была давно закоммичена;
- индекс `runs_single_active_idx` начинает блокировать **все** последующие запуски.

Итог: сервис молча перестаёт работать после первого же падения. Отказ выглядит как
нормальная работа — самый опасный класс ошибок.

## Ключевой вопрос: как отличить мёртвый запуск от живого

Требование Product/Tech Lead: не использовать критерий «running старше N минут» без
обоснования.

### Отвергнутые варианты

**A. `started_at < now() - N минут`.**
Отвергнут. `started_at` фиксирует начало, а не активность. Батч, замедленный
rate limit'ом или долгими LLM-вызовами, был бы признан мёртвым и завершён **параллельно
с реальной работой** — прямое нарушение требования «не конфликтовать с работающим run».
Любое значение N является либо слишком агрессивным, либо слишком терпимым.

**B. Проверка PID процесса.**
Отвергнут. PID переиспользуются операционной системой; в контейнерах PID почти всегда 1.
Проверка «жив ли процесс с таким PID» из другого контейнера невозможна.

**C. Только heartbeat.**
Работоспособен, но требует выбора порога и остаётся эвристикой: «heartbeat не обновлялся
N минут» может означать и зависший, но живой процесс.

### Принятое решение: двухуровневый критерий

Проверка выполняется в порядке убывания достоверности.

#### Уровень 1 (основной, детерминированный) — advisory lock в `pg_locks`

Установленные факты **[ПРОВЕРЕНО 2026-09-07]**:

| Наблюдение | Результат |
|---|---|
| Пока сессия жива, блокировка видна из другой сессии | `classid=1, objid=525132706, granted=true` |
| После обрыва соединения | Записи в `pg_locks` **нет** |
| Раскладка 64-битного ключа | `classid = key >> 32`, `objid = key & 0xFFFFFFFF` |

Отсутствие блокировки в `pg_locks` — **признак того, что владевший ею процесс
завершился**. Это факт состояния СУБД, а не предположение о времени.

> Техническая деталь: `pg_locks.objid` имеет тип OID (uint32), поэтому 64-битный ключ
> нельзя сравнивать напрямую — он раскладывается на две 32-битные части. Обнаружено
> при проверке: наивное сравнение падает с ошибкой `value out of range for type oid`.

#### Уровень 2 (вспомогательный) — heartbeat

Применяется только когда `lock_key IS NULL` (запуск создан до этой миграции либо
блокировка не была зафиксирована). Порог `HEARTBEAT_TIMEOUT_MINUTES` (по умолчанию 15)
взят с запасом относительно целевой длительности батча (≤10 минут) и осознанно
консервативен: лучше не восстановить мёртвый запуск сейчас, чем прервать живой.

**Итоговое правило:**

```
orphaned(run) :=
     run.status = 'running'
 AND (
       -- основной критерий: держатель блокировки исчез
       (run.lock_key IS NOT NULL AND NOT exists_in_pg_locks(run.lock_key))
    OR -- запасной критерий для записей без lock_key
       (run.lock_key IS NULL AND run.heartbeat_at < now() - heartbeat_timeout)
     )
```

## Безопасность восстановления

### Не конфликтует с работающим запуском
Пока процесс жив, он удерживает advisory lock, и запись присутствует в `pg_locks` — такой
запуск никогда не будет признан осиротевшим. Живой процесс дополнительно обновляет
`heartbeat_at`.

### Два процесса не восстановят один запуск
Восстановление выполняется одним условным `UPDATE`:

```sql
UPDATE runs SET status = 'failed', ...
WHERE id = $1 AND status = 'running'
RETURNING id
```

Блокировка строки в PostgreSQL сериализует конкурентные попытки: второй процесс увидит
статус уже изменённым, его `WHERE` не совпадёт, и он получит пустой результат. Событие в
`run_events` пишется **только** тем процессом, чей `UPDATE` вернул строку.

Дополнительно вся процедура выполняется под отдельным advisory lock recovery
(`RECOVERY_LOCK_ID`), поэтому параллельные старты не выполняют её одновременно.

### Идемпотентность
Повторный запуск recovery не находит запусков в статусе `running` и не выполняет действий.
Условие `AND status = 'running'` делает `UPDATE` идемпотентным по построению.

## Результат восстановления

Осиротевший запуск переводится в **`failed`** (не `completed`): его работа не была
доведена до конца, и отчётность не должна утверждать обратное. Заполняются
`recovered_at`, `recovery_reason`, `finished_at`, `error`.

Заявки (`daily_claims`) этого запуска **не трогаются** — ими занимается reaper по
истечении lease (ADR-0004). Разделение намеренное: recovery отвечает за строку `runs`,
reaper — за заявки. Смешение двух механизмов создало бы риск досрочного освобождения
заявок, которые ещё могут обрабатываться.

## Последствия

**Положительные**
- Сервис самовосстанавливается после падения без ручного вмешательства.
- Критерий опирается на состояние СУБД, а не на таймаут-эвристику.
- Причина восстановления сохраняется в `run_events` для аудита.

**Отрицательные**
- Две дополнительные колонки и индекс.
- Живой процесс обязан обновлять `heartbeat_at`; при отсутствии обновления запуск с
  `lock_key IS NULL` может быть восстановлен ошибочно. Митигация — заполнять `lock_key`
  всегда, heartbeat остаётся резервным путём.

## Проверяемость

- Тест: обычный старт без осиротевших запусков не производит изменений.
- Тест: запуск с исчезнувшей блокировкой восстанавливается и получает `failed`.
- Тест: параллельный старт — восстановление происходит ровно один раз.
- Тест: повторный вызов recovery ничего не делает (идемпотентность).
- Тест: запуск с действующей блокировкой **не** трогается.
- Тест: причина восстановления записана в `run_events`.
