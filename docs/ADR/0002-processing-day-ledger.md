# ADR-0002: Реестр processing day (processing_day + daily_claim)

**Статус:** Принято
**Дата:** 2026-09-07
**Решение принял:** Product/Tech Lead
**Связано с:** OQ-1, OQ-13, OQ-14

---

## Контекст

ТЗ задаёт правила выборки игр:

1. Каждый новый день сначала обрабатываются первые 20 игр из **New Releases**.
2. Затем последовательно обрабатываются игры из **See All**.
3. При каждом запуске выбираются **следующие необработанные сегодня** игры.
4. На следующий день цикл начинается заново.
5. Существующая игра **обновляется**, а не создаётся повторно.

Это требует persistent-состояния: «что уже обработано сегодня» и «где мы находимся в
листинге». Состояние обязано переживать перезапуск приложения.

### Критическая находка Discovery

**[ПРОВЕРЕНО, окончательно уточнено 2026-09-07]** История измерений:

1. Первое измерение: «17 из 33 ссылок» — **ошибка**, считались все ссылки `/game/<slug>/`,
   включая промо-блоки шапки, одинаковые на всех страницах.
2. Второе измерение (по карточкам): **0 пересечений** — но снимки делались по одному.
3. **Третье измерение (фикстуры, снятые с интервалом ~1.3 с): 5 пересечений из 20.**
   Игры сместились по позициям: 1→4, 2→3, 15→17, 16→18, 17→19.

Третий замер и есть решающий: он показывает **дрейф листинга во времени**, а не дубли
внутри одного снимка. Список отсортирован по дате релиза по убыванию и включает будущие
даты; новые игры непрерывно вставляются сверху, сдвигая остальные вправо. За 1.3 секунды
сместилось 5 из 20 позиций — за час между запусками сдвиг будет значительно больше.

**Следствие:** логика «одна страница за запуск» повторно читала бы уже обработанные игры и
**молча пропускала** другие, попавшие в «слепую зону» между снимками.

**Решение:** номер страницы — только *подсказка*. Источник истины — реестр `daily_claims`:
уже заявленные слаги отбрасываются, и планировщик листает страницы, пока не наберёт нужное
число действительно новых игр. Парсер при этом возвращает страницу как есть и не пытается
дедуплицировать между страницами — это ответственность оркестрации.

## Рассмотренные варианты

### A. Хранить только номер страницы
- ➕ Минимальное состояние.
- ❌ Ломается из-за нестабильности листинга (см. выше): пропуски и повторы.

### B. Только реестр обработанных игр, без курсора
- ➕ Пропуски исключены.
- ➖ Каждый запуск начинает с первой страницы — растёт число запросов к Metacritic.

### C. Реестр + курсор, где источник истины — реестр (выбрано)
- ➕ Пропуски исключены реестром.
- ➕ Курсор избавляет от повторного листания с начала.
- ➕ Пересечение страниц становится безвредным.
- ➖ Две таблицы вместо одной.

## Решение

Принят **вариант C**.

```sql
processing_day (
  day DATE PRIMARY KEY,
  phase TEXT NOT NULL,          -- 'new_releases' | 'browse' | 'exhausted'
  browse_page INT NOT NULL DEFAULT 1,
  new_releases_done BOOLEAN NOT NULL DEFAULT FALSE
);

daily_claim (
  day DATE NOT NULL,
  source TEXT NOT NULL,
  source_slug TEXT NOT NULL,
  status TEXT NOT NULL,
  PRIMARY KEY (day, source, source_slug)
);
```

**Ключевое правило: номер страницы — подсказка, реестр — источник истины.**
Планировщик листает страницы, отбрасывая уже заявленные слаги, пока не наберёт 20 новых.

### Граница суток

`day` вычисляется по **UTC**, timezone конфигурируется через `PROCESSING_TIMEZONE`
(решение по OQ-1). Время сервера не используется — оно недетерминировано и уязвимо к
переводу часов.

### Сброс на новый день

Новый день → строки в `processing_day` нет → создаётся с `phase='new_releases'`,
`browse_page=1`. Цикл начинается заново автоматически, без отдельной задачи очистки.

### Почему план вычисляется из БД, а не из счётчиков

План батча выводится из состояния БД, а не из числа выполненных запусков. Поэтому он
автоматически корректен после перезапуска, пропущенных тиков cron и ручных запусков —
отдельная логика «навёрстывания» не нужна.

## Последствия

**Положительные**
- Требования 1–4 из ТЗ выполняются буквально и проверяемо.
- Пропуск игр структурно невозможен.
- Пропущенные тики безопасны.

**Отрицательные**
- `daily_claim` растёт на ~20 строк в час. За год ≈ 175 тыс. строк — незначительно, но
  задача периодической очистки старых дней вносится в roadmap.

## Проверяемость

- Тест: два прогона подряд не обрабатывают одну игру дважды.
- Тест: при пересечении страниц ни одна игра не пропущена.
- Тест: смена суток сбрасывает фазу на `new_releases`.
